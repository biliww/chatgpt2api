# 浏览器注册机技术方案（无头 / 有头）

> 落地目录：`scripts/register-my/`（代码已就绪）
> 方案文档：`docsMy/技术实现/注册/浏览器注册机技术方案.md`

## 1. 背景与目标

当前项目的注册机（`services/register/`）使用 `curl_cffi` 直接模拟 OpenAI / Auth0 的
注册 API（authorize → user/register → email-otp → create_account → token 交换），并手写
Sentinel PoW / SO-Token 以绕过 Cloudflare。这种方式：

- 维护成本高：OpenAI 一旦调整接口、加密参数或挑战强度，脚本就要跟着改；
- 反爬对抗被动：PoW / SO-Token 需要持续逆向；
- 对“真人环境”的还原度有限。

本方案新增一块**浏览器注册机**：用真实 Chromium（Playwright）走完 OpenAI 注册 UI，由浏览器
原生处理 Cloudflare / Turnstile / Sentinel 挑战；**邮箱验证完整复用现有架构**
（`services/register/mail_provider`，支持 9 种 provider，默认 `tempmail_lol`），注册成功后从
浏览器会话中提取登录态产出账号。

目标：

1. 提供“浏览器 + 邮箱复用”的注册通路，作为 API 通路的互补/兜底；
2. 支持**无头（headless）**与**有头（headed）**两种模式；
3. 邮箱验证复用本架构，支持不同 provider，默认 `tempmail_lol`；
4. 不破坏现有 Web 注册机，新增代码自包含、可独立运行。

## 2. 可行性结论（先说结论）

- ✅ **邮箱验证复用本架构可行**：`mail_provider.create_mailbox` / `wait_for_code` 是纯函数式
  封装，浏览器注册机直接 import 复用，无需任何改造成本。
- ✅ **浏览器驱动可行**：Playwright + Chromium 可完整驱动 OpenAI 注册页；无头模式适合服务器，
  有头模式适合本地校准。
- ⚠️ **前置依赖**：环境需安装 `pip install playwright && playwright install chromium`
  （Chromium 二进制约 150MB，本环境当前未下载，属一次性步骤）。本项目当前**没有系统 Chrome**，
  因此浏览器二进制必须下载。
- ⚠️ **选择器时效性**：OpenAI 注册页 DOM / 文案随版本变化，首次上线前需用 `--headed`
  模式跑通一次并按实际页面校准（代码已用“语义定位 + 多候选 + 失败截图”降低脆弱性）。

## 3. 整体架构

```text
┌──────────────────────────────────────────────────────────────┐
│  cli.py  （命令行入口 / 并发线程池 / 结果输出）                  │
│      │  total / threads / headless / proxy / dry-run          │
│      ▼                                                        │
│  config.py  （加载并规范化配置，复用 config-register.json）      │
│      │                                                        │
│      ▼                                                        │
│  register.py  BrowserRegistrar.register()                     │
│      ├──────────────┐                                         │
│      ▼              ▼                                         │
│  browser.py     mailbox.py  ──▶ services.register.mail_provider│
│  (Playwright    (薄封装,      （9 种 provider，默认 tempmail_lol）│
│   Chromium)      复用本架构)                                      │
│      │              │                                         │
│      │   创建邮箱 / 轮询 OTP                                     │
│      └──────┬───────┘                                         │
│             ▼                                                 │
│  浏览器走完注册 UI → 提取 token / cookie → 产出账号              │
│             │                                                 │
│             ▼                                                 │
│  结果输出：本地号池(add_account_items) / JSONL / 远程 /api/accounts│
└──────────────────────────────────────────────────────────────┘
```

关键原则：**邮箱逻辑只有一份**（在 `services/register/mail_provider.py`），浏览器注册机与
Web 注册机共用。新增 / 修复邮箱 provider 只需改一处。

## 4. 与现有 Web 注册机的关系

| 维度 | Web 注册机（`services/register`） | 浏览器注册机（`scripts/register-my`） |
|------|-----------------------------------|----------------------------------------|
| 注册方式 | `curl_cffi` 模拟 Auth0 / OpenAI API | 真实浏览器走 UI |
| 反爬对抗 | 手写 Sentinel PoW / SO-Token（见 `openai_register.py`） | 浏览器原生处理 CF / Turnstile / Sentinel |
| 邮箱验证 | 复用 `mail_provider` | **同样复用 `mail_provider`** |
| 运行形态 | Web 面板 + 后端线程池（`service.py`） | 独立脚本，可命令行 / 定时任务 |
| 结果输出 | 写本地号池 | 号池 / JSONL / 远程（可配） |
| 合并影响 | 已做成可选路由，合 main 低冲突 | 完全独立目录，零冲突 |

两者可长期共存：API 通路稳就继续用，遇到 Cloudflare 升级导致 API 通路大面积失败时，切到
浏览器通路兜底。

## 5. 浏览器驱动选型：Playwright（Chromium）

选择 Playwright 的理由：

- 原生支持 `headless` / `headed` 切换，满足“无头 + 有头”双需求；
- 提供语义定位器（`get_by_text` / `get_by_label`），对 DOM 微调更鲁棒；
- 可注入 `add_init_script` 抹掉 `navigator.webdriver` 痕迹，降低反爬识别；
- 每个任务用独立 `BrowserContext`，cookie / localStorage 天然隔离，避免串号。

> 为什么不直接用 Selenium：Playwright 的语义定位器与上下文隔离更贴合本场景，且本项目
> Node 侧已具备 Playwright 生态。若后续需要，可在 `browser.py` 的 `Browser` 类后增加
> 第二个 backend（保持同一接口），不影响上层 `register.py`。

## 6. 邮箱验证：复用本架构

`mailbox.py` 仅做薄封装，直接 `from services.register import mail_provider`：

```python
def create_mailbox(mail_config, username=None):
    return mail_provider.create_mailbox(mail_config, username)

def wait_for_code(mail_config, mailbox):
    return mail_provider.wait_for_code(mail_config, mailbox)
```

`mail_config` 结构与 `config-register.json` 的 `"mail"` 字段完全一致。provider 选择逻辑、
默认 `tempmail_lol`、启停开关（`enable`）、轮询配置（`wait_timeout` / `wait_interval`）全部沿用，
无需重新实现。代码中默认 behavior：仅启用 `tempmail_lol` 时即走 `tempmail_lol`。

## 7. 注册流程详述

浏览器内流程（集中在 `register.py` 的 `_signup`）：

```text
1) 打开 https://chatgpt.com/ ，点击 “Sign up”
2) 填写邮箱(input[type=email]) → 点击 Continue
3) 填写密码(input[type=password]) → 点击 Continue
4) 触发验证码后，回到 mail_provider 轮询 OTP（wait_for_code）
5) 在浏览器填写验证码 → 点击 Continue
6) 填写姓名(First/Last name) + 生日(date / 月日年 select) → Continue
7) 等待 URL 落地到 chatgpt.com（非 auth/login）→ 稳定 3s
8) 提取登录态：
     - fetch('/api/auth/session') → accessToken / idToken
     - context.cookies() → refresh_token / session_token
9) 产出账号：
     { email, password, access_token, refresh_token, id_token,
       session_token, source_type:"browser", created_at }
```

OTP 处理要点：验证码页面出现后，浏览器侧不自己解析邮件，而是**复用 mail_provider 的
`wait_for_code`** 在后台轮询真实邮箱，拿到 6 位码后再填回浏览器。这样“收邮件 + 解析验证码”
完全复用既有、已验证的逻辑。

Token 提取策略：以 `/api/auth/session` 的 `accessToken` 为主，`refresh_token` /
`session_token` 从 cookie 补充；若某环境只下发 `accessToken`，仍可写入号池并靠
`account_service.refresh_accounts` 校验。 `session_token`（next-auth 会话 cookie）一并保存，
便于后续做会话恢复。

## 8. 配置设计

复用 `config-register.json` 的 `mail` / `proxy` / `total` / `threads` 结构，新增两段：

```jsonc
{
  "mail": { /* 与现有完全一致，provider 默认 tempmail_lol */ },
  "proxy": "",
  "total": 1,
  "threads": 1,
  "browser": {
    "headless": true,              // 无头/有头（CLI --headed 可覆盖）
    "user_agent": "Mozilla/5.0 ... Chrome/145.0.0.0 ...",
    "viewport": { "width": 1280, "height": 800 },
    "args": [],                    // 额外 Chromium 启动参数
    "executable_path": "",         // 留空则自动查找；可指向自有 Chromium
    "timeout": 30000,
    "proxy": "",                   // 未填则继承顶层 proxy
    "save_failure_screenshot": true,
    "screenshot_dir": "data/register-my-screenshots"
  },
  "output": {
    "write_pool": true,            // 是否写入本地号池(add_account_items)
    "jsonl_path": "data/register-my-results.jsonl",
    "remote_base_url": "",         // 非空则 POST 远程 /api/accounts
    "remote_admin_key": ""
  }
}
```

加载逻辑见 `config.py`：`proxy` 未显式设置时继承顶层 `proxy`；`providers` 无 `enable`
时报错；与现有 Web 注册机共用同一份 `config-register.json` 时，邮箱/代理配置天然同步。

## 10. 反爬 / 隐匿策略

- **抹 webdriver 痕迹**：`page.add_init_script` 重写 `navigator.webdriver = undefined`；
  启动参数加 `--disable-blink-features=AutomationControlled`。
- **真实 UA / 视口**：默认 Chrome/145 UA，视口 1280×800（可在配置覆盖）。
- **上下文隔离**：每个任务独立 `BrowserContext`，cookie / localStorage 不串号。
- **有头优先校准**：首次用 `--headed` 跑通，确认选择器与真人流程一致后再切无头批量。
- **代理**：`browser.proxy` 可逐任务不同（配合 `threads` 并发时建议每任务独立代理，避免同 IP
  批量注册被风控）。

## 11. 并发模型

`cli.py` 用 `ThreadPoolExecutor(max_workers=threads)`：

- 每个任务 `run_one()` 新建一个 `BrowserRegistrar`（= 一个独立浏览器进程 + 上下文），天然隔离；
- 提交节奏：`len(futures) < threads` 且 `submitted < total` 时持续提交；
- `FIRST_COMPLETED` 回收完成任务，统计 success / fail；
- 结果与错误实时日志输出，成功结果交给 `sink`（号池 / JSONL / 远程）。

> 规模优化（可选）：若 `threads` 较大，可改造为“单浏览器 + 多上下文”，减少进程开销。
> 当前实现优先正确性，每个任务独立浏览器进程。

## 12. 与 Web 面板 / API 集成（可选增强）

当前浏览器注册机是**独立脚本**，不依赖 Web 面板。后续若希望从面板启动，可低成本接入：

1. 在 `config-register.json` 增加 `mode` 概念：`"api"`（现有 curl 通路）/ `"browser"`
   （新通路）；
2. `api/register.py` 的 `start_register` 按 `mode` 分流到不同的 worker（现有
   `openai_register.worker` vs 新增 `register-my` 的 `run_one`）；
3. 复用现有 `/api/register/events` SSE 日志通道（把 `register.py` 的 `log` 回调接到 SSE sink）。

该增强不影响已落地的脚本运行，按需实施。

## 13. 失败处理与重试

- 单任务异常时在 `finally` 关闭浏览器，并保存失败截图（`save_failure_screenshot`）；
- `register.py` 的 `register()` 抛出异常，由 `cli.py` 捕获计入 fail；
- 邮箱维度：`mail_provider` 内部已对多 provider 做轮询兜底（如 DDG 日上限自动切换）；
- 远程写入失败：建议保持 `jsonl_path` 本地备份，便于后续重放（同 `register_外置注册脚本` 方案）。

## 14. 分阶段实施路线

- **P0（已落地）**：脚本化浏览器注册机，复用 mail_provider，支持无头/有头、并发、结果输出。
- **P1（建议）**：在 `--headed` 下针对当前 OpenAI 页面校准选择器；补充每任务独立代理池。
- **P2（可选）**：接入 Web 面板（browser 模式开关 + SSE 日志）；增加失败重放；增加
  纯 Python Playwright 之外的 backend 抽象（如需）。

## 15. 验收标准

1. `python scripts/register-my/cli.py --dry-run` 能加载并校验配置（含 provider 检查）；
2. 安装 `playwright` + `playwright install chromium` 后，`--headed` 模式可在本地跑通一次完整注册；
3. 注册成功的账号能写入本地号池（`write_pool=true`）或 JSONL（`jsonl_path`）；
4. 邮箱验证完全走 `mail_provider`，未重新实现任何邮箱协议；
5. 失败任务有截图与清晰日志，不会污染其他任务上下文；
6. 无头模式可在服务器批量运行。

## 16. 风险与缓解

| 风险 | 缓解 |
|------|------|
| OpenAI 注册页改版导致选择器失效 | `--headed` 校准；失败截图；语义定位 + 多候选 |
| Chromium 二进制未安装 | 文档明确 `playwright install chromium`；启动报错给出安装提示 |
| 同 IP 批量注册被风控 | 每任务独立代理；有头模式拟人节奏；控制并发 |
| token 提取不全（仅 accessToken） | 保存 session_token；靠 refresh_accounts 校验 |
| 浏览器资源占用 | 控制 threads；任务结束 `finally` 关闭浏览器 |

## 17. 运行速查

```bash
# 1) 安装（一次性）
pip install -r scripts/register-my/requirements-register-my.txt
playwright install chromium

# 2) 校验配置
python scripts/register-my/cli.py --dry-run

# 3) 有头模式跑通 1 个（首次校准）
python scripts/register-my/cli.py --headed --total 1

# 4) 无头批量
python scripts/register-my/cli.py --total 10 --threads 2
```
