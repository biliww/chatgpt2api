## 0. 背景与目标

### 0.1 问题回顾
合并提交 `4159feb2` 把 `main` 合入 `main-my`。由于 `main` 从未包含 register（注册机）功能，
合入时 register 相关代码被整文件删除，且 7 个共享文件里的 register 引用被一并清除。

### 0.2 为何放弃"恢复式"方案
旧方案是把功能**重新接回** `api/app.py`、`top-nav.tsx`、`web/src/lib/api.ts`、
`web/src/app/settings/store.ts`、`services/backup_service.py` 等文件。
但这些文件正是 `main` 在每次迭代中**高频改动**的文件（上一轮合并里 `api/app.py`、`top-nav.tsx`、
`store.ts`、`api.ts`、`backup_service.py`、`config.json` 均有变更）。
把功能焊死在这些文件上，意味着**未来每次 `merge main` 都极易再次冲突 / 被丢弃**，治标不治本。

### 0.3 新目标
写一套**自包含、独立**的注册功能，做到：
1. 业务逻辑全部落在**新增文件**，不（或仅以一次性稳定方式）改动 `main` 高频文件；
2. 未来 `merge main` 时几乎全自动合并，影响面小、冲突可一行修复；
3. 功能等价于原 register：邮箱批量注册 OpenAI 账号、并发控制、实时日志、写回号池。

## 1. 设计原则（合并友好是硬约束）

1. **新增文件优先**：所有功能代码放在新文件 / 新目录。git 合并时，新增文件永不产生冲突。
2. **零侵入高 churn 文件**：**禁止**编辑以下文件——
   `web/src/lib/api.ts`、`web/src/app/settings/store.ts`、`services/backup_service.py`、
   `services/config.py`、`config.json`。（这些文件由 `main` 主导，编辑即埋雷。）
3. **一次性稳定接入点**：仅对 `api/app.py` 与 `web/src/components/top-nav.tsx` 做
   **一次性、写入后不再变更**的接入，且接入方式通过两个"扩展点"新文件承载后续扩展，
   后续加功能**不再动**这两个文件。
4. **配置自管理**：注册配置存 `data/register.json`（运行时文件，`main` 不碰 `data/`），
   不写入 `config.json` / `services.config`。
5. **备份解耦**：不接入主备份功能；在注册页面内提供**导入 / 导出**按钮（下载/上传 `data/register.json`）。

## 3. 后端设计

### 3.1 特性注册表 `api/feature_registry.py`（★ 扩展点）
把所有"可选 / 本地功能"的路由集中登记，使 `api/app.py` 只改一次：

```python
from fastapi import APIRouter

_OPTIONAL_ROUTERS: list[APIRouter] = []


def register_optional_router(router: APIRouter) -> None:
    _OPTIONAL_ROUTERS.append(router)


def get_optional_routers() -> list[APIRouter]:
    return _OPTIONAL_ROUTERS
```

`api/register.py` 在模块加载时调用 `register_optional_router(create_router())` 完成自注册。
之后新增任何本地功能，都只改本文件（或让功能模块自注册），**不再触碰 `api/app.py`**。

### 3.2 `api/app.py` 一次性接入（稳定，不再变更）
在现有 `app.include_router(...)` 之后、`@app.api_route("/{full_path:path}"...)` 之前插入：

```python
from api.feature_registry import get_optional_routers
...
for _r in get_optional_routers():
    app.include_router(_r)
```

> 必须在 catch-all 路由**之前**注册，否则 `/api/register*` 会被静态兜底路由拦截。
> 此改动只做一次；未来 `main` 即便改了 `api/app.py` 的其它区域（新增自己的路由、改 catch-all 等），
> 3-way 合并通常能同时保留双方；偶发冲突也只需把这两行 `for` 循环保留回来，一行可恢复。

### 3.3 路由 `api/register.py`
- `GET  /api/register`        返回当前配置 + 实时 stats / logs
- `POST /api/register`        更新配置（字段校验后落地 `data/register.json`）
- `POST /api/register/start`  启动注册任务
- `POST /api/register/stop`   停止任务
- `POST /api/register/reset`  重置 stats / logs
- `GET  /api/register/events` SSE 实时日志流（token 从 query 读取：`?token=...`）

鉴权：沿用 `api.support.require_admin`（已在 HEAD 中确认存在，无需新增）。
SSE 端点用 `EventSource` 订阅，与前端 `page.tsx` 对齐。

### 3.4 配置与持久化 `services/register/config.py`
- 路径：`services.config.DATA_DIR / "register.json"`（沿用项目约定，`main` 不碰 `data/`）。
- 结构（复用已验证模型）：

```json
{
  "enabled": false,
  "mail": { "request_timeout": 30, "wait_timeout": 120, "wait_interval": 3, "providers": [] },
  "proxy": "",
  "total": 1,
  "threads": 1,
  "mode": "total",
  "target_quota": 100,
  "target_available": 10,
  "check_interval": 5,
  "stats": { "success": 0, "fail": 0, "done": 0, "running": 0, "threads": 1 }
}
```

- 提供 `_default_config()` / `_normalize()` / `load()` / `save()`，**完全自包含**，
  不依赖 `services.config` 的业务配置逻辑。其它模块通过 `register_service` 单例读写。

### 3.5 业务逻辑 `mail_provider` / `openai_register` / `service`
- 直接以 `6c59723` 中可恢复的旧实现（`services/register/mail_provider.py` 990 行、
  `openai_register.py` 558 行、`register_service.py` 197 行）作为**基础**，
  但**重构为独立模块**：不依赖任何共享业务模块，仅依赖 `curl_cffi`（项目已用）与本项目常量。
- `service.py`：单例 `register_service`，管理线程池、并发注册、stats、logs；
  通过回调把日志推送给 SSE。
- 复用 `account_service.add_account_items` / `refresh_accounts`（HEAD 中已确认存在）
  把注册结果写回号池——这两个符号属于 `main` 保留的接口，稳定可用。

## 4. 前端设计

### 4.1 私有 API 客户端 `web/src/lib/register-api.ts`（★ 不碰 api.ts）
```ts
import { httpRequest } from "@/lib/request";

export type RegisterConfig = {
  enabled: boolean;
  mail: { request_timeout: number; wait_timeout: number; wait_interval: number; providers: Array<Record<string, unknown>>; };
  proxy: string;
  total: number;
  threads: number;
  mode: "total" | "quota" | "available";
  target_quota: number;
  target_available: number;
  check_interval: number;
  stats: { success: number; fail: number; done: number; running: number; threads: number; [k: string]: unknown; };
  logs?: Array<{ time: string; text: string; level: string }>;
};

export async function fetchRegisterConfig() {
  return httpRequest<{ register: RegisterConfig }>("/api/register");
}
export async function updateRegisterConfig(updates: Partial<RegisterConfig>) {
  return httpRequest<{ register: RegisterConfig }>("/api/register", { method: "POST", body: updates });
}
export async function startRegister() {
  return httpRequest<{ register: RegisterConfig }>("/api/register/start", { method: "POST" });
}
export async function stopRegister() {
  return httpRequest<{ register: RegisterConfig }>("/api/register/stop", { method: "POST" });
}
export async function resetRegister() {
  return httpRequest<{ register: RegisterConfig }>("/api/register/reset", { method: "POST" });
}
```

### 4.2 私有状态 `web/src/app/register/store.ts`（★ 不碰 settings/store.ts）
独立的 zustand store，内部调用 `register-api.ts`：
- 状态：`registerConfig`、`isLoading`、`isSaving`、`logs`
- actions：`loadRegister()`、`setRegisterConfig()`、`startRegister()`、`stopRegister()`、`resetRegister()`、
  `setRegisterProxy / setRegisterTotal / setRegisterThreads / setRegisterMode / setRegisterTargetQuota / setRegisterTargetAvailable / setRegisterCheckInterval`
- 导入 / 导出：`exportConfig()`（下载 `data/register.json`）、`importConfig(file)`（上传恢复）

### 4.3 页面 `web/src/app/register/page.tsx`
- `'use client'`，用 `useAuthGuard()` 守卫（与现有管理页同款，签名 `useAuthGuard(allowedRoles?)`）。
- 用 `new EventSource(\`${apiUrl}/api/register/events?token=${token}\`)` 订阅实时日志。
- 渲染 `RegisterCard`；提供启动 / 停止 / 重置 / 配置表单 / 导入导出按钮。

### 4.4 导航 `web/src/config/nav.ts`（★ 扩展点）+ `top-nav.tsx` 一次性改动
`web/src/config/nav.ts`：
```ts
export const optionalNavItems: Array<{ href: string; label: string; roles?: string[] }> = [
  { href: "/register", label: "注册机", roles: ["admin"] },
];
```
`top-nav.tsx` 一次性改动：渲染导航时把 `optionalNavItems` 拼接进去（**不改 `adminNavItems` 本体**）：
```tsx
const navItems = session?.role === "admin"
  ? [...adminNavItems, ...optionalNavItems]
  : [...userNavItems, ...optionalNavItems];
```
> 关键点：`adminNavItems` 数组本体保持不动。这样 `main` 对该数组的改动（上轮合并它就改过）
> 能干净合并；注册入口来自新文件 `nav.ts`，互不干扰。

## 6. 实施步骤（建议顺序）

1. **后端骨架**：`services/register/__init__.py` + `config.py`，先跑通 `GET/POST /api/register`（读写 `data/register.json`）。
2. **接入点**：新增 `api/feature_registry.py`；在 `api/app.py` 做一次性接入；启动校验 `/api/register` 返回 200。
3. **业务逻辑**：基于 `6c59723` 可恢复旧逻辑，重写 `mail_provider.py` / `openai_register.py` / `service.py` 为独立模块。
4. **补全路由**：`api/register.py` 补齐 `start / stop / reset / events(SSE)`。
5. **前端客户端与状态**：`register-api.ts` → `store.ts`。
6. **前端页面**：`register-card.tsx` → `page.tsx`（含 SSE、导入导出）。
7. **导航**：`config/nav.ts` + `top-nav.tsx` 一次性拼接。
8. **自测**：页面配置 / 启动 / 实时日志；导入导出 `data/register.json`。

> 步骤 1–2 完成后即具备"合并友好骨架"，后续 3–7 全是新增文件，可并行推进、互不阻塞。

## 7. 合并策略（如何保证 future merge 友好）

- **功能代码全为新增文件** → `git merge main` 时 git 自动合入，**无冲突**。
- 仅 `api/app.py` 与 `top-nav.tsx` 两个一次性改动需关注：
  - `api/app.py`：若 `main` 也改了 include 区，3-way 合并通常保留双方；偶发冲突只需把
    `for _r in get_optional_routers(): app.include_router(_r)` 保留回来。
  - `top-nav.tsx`：我们**未改 `adminNavItems` 本体**，仅拼接 `optionalNavItems`，冲突概率低；
    即便冲突也只发生在拼接行，一行可修。
- 把"合并友好"作为本功能的**硬约束**：任何改动都不得编辑
  `api.ts` / `settings/store.ts` / `backup_service.py` / `config.py` / `config.json`。
- （可选）加 `scripts/check_register_isolated.sh` 做回归：断言"新增文件集合"且"未触碰高 churn 文件"。

## 8. 风险与回滚

- **风险 A**：feature_registry 接入遗漏 → `/api/register` 404。对策：启动后 `curl` 验证。
- **风险 B**：`mail_provider` / `openai_register` 依赖上游接口变动 → 影响被隔离在本模块内，不波及主流程；
  修复只改 `services/register/` 下文件（新增文件，合并安全）。
- **回滚**（纯新增 + 2 个一次性接入）：
  ```bash
  git checkout HEAD -- api/app.py web/src/components/top-nav.tsx
  rm -rf api/feature_registry.py api/register.py services/register \
         web/src/app/register web/src/lib/register-api.ts web/src/config/nav.ts
  ```

## 9. 与"恢复式"方案对比

| 维度 | 旧恢复方案 | 本独立方案 |
|------|-----------|-----------|
| 是否改 `api.ts` / `settings/store.ts` | **是**（高冲突风险） | **否**（私有模块） |
| 是否改 `backup_service` / `config` | **是** | **否**（页面内导入导出） |
| 未来 `merge main` 影响 | 每次可能丢失 / 冲突 | **几乎全自动合并** |

| 接入点数量 | 7 个共享文件均被改 | **2 个一次性接入点** + 4 个扩展点新文件 |
